## 1. Resend domain verification

Do this once per sending domain, in the Resend dashboard:

1. Add `shilevi.com` (primary transactional sender) and `shilevi.app` if it will also send.
2. Add the DNS records Resend shows:
   - **SPF**: a TXT record on the sending subdomain (commonly `send`) with the SPF include
     Resend provides. Do not create a second SPF record on the same name.
   - **DKIM**: the CNAME/TXT records Resend provides. Keep them exactly as shown.
   - **DMARC**: start with `v=DMARC1; p=none; rua=mailto:dmarc@shilevi.com` and tighten to
     `quarantine`/`reject` only after monitoring. DMARC needs a valid SPF or DKIM alignment.
3. Wait for Resend to report **Verified**. A DNS record created is not proof of verification.
4. Send a test message to a real mailbox you control and inspect the headers for
   `spf=pass` and `dkim=pass`.

Do not set `RESEND_FROM_EMAIL` to a domain that is not verified. Sending will fail or be rejected.

## 2. Supabase Auth SMTP (verification, recovery, security)

In Supabase → Authentication → SMTP Settings, use Resend's SMTP service:

```text
Host: smtp.resend.com
Port: 465
Encryption: SSL/TLS
Username: resend
Password: <RESEND_API_KEY>       # keep in Supabase only, never in this repo
Sender name: Shilevi
Sender email: no-reply@shilevi.com
```

If port 465 is blocked in your environment, use port 587 with STARTTLS. Do not disable TLS
verification.

Then configure Auth → URL Configuration:

- **Site URL**: `https://shilevi.app`
- **Redirect allow list**: `https://shilevi.app/auth/callback`, `https://shilevi.com/auth/callback`,
  and `http://localhost:3000/auth/callback` for local development only.
- Enable **Confirm email** if you want verification before normal use.
- Set a sensible session/JWT expiry and enable refresh-token rotation.

The app callback is `src/app/auth/callback/route.ts`; it exchanges the code for a session and
redirects to a same-site `next` path. It rejects absolute/off-site redirect targets.

### Auth email templates

Edit these in Supabase → Authentication → Email Templates. Keep the links as
`{{ .ConfirmationURL }}` (or the recovery equivalent) so tokens are generated by Supabase, and use
the same brand header as the app:

| Template | Purpose | Required link |
|---|---|---|
| Confirm signup | Verify a new account | `{{ .ConfirmationURL }}` |
| Magic link | Passwordless sign-in, if enabled | `{{ .ConfirmationURL }}` |
| Recovery | Password reset | `{{ .ConfirmationURL }}` |
| Invite | Staff invitation, if used | `{{ .ConfirmationURL }}` |
| Change email address | Confirm a new address | `{{ .ConfirmationURL }}` |

Never put passwords, M-Pesa PINs, card numbers or identity documents in an email. Recovery links
expire; do not extend them casually.

## 3. Application notifications

Security-definer triggers enqueue rows in `public.notification_outbox` on:

- provider application status changes (`application_status`);
- ride status changes for both parties (`ride_status`);
- property verification decisions (`property_verification`);
- payout status changes (`payout_status`).

Payloads contain identifiers and statuses only. Recipients are resolved from `auth.users.email` at
enqueue time and are not exposed to the browser. The outbox has RLS and no client insert policy.

The dispatcher is `POST /api/notifications/dispatch`:

```text
x-dispatch-secret: <NOTIFICATION_DISPATCH_SECRET>
```

Environment:

```text
RESEND_API_KEY=
RESEND_FROM_EMAIL=Shilevi <no-reply@shilevi.com>
NOTIFICATION_DISPATCH_SECRET=
SUPABASE_SERVICE_ROLE_KEY=
```

It drains up to 20 due messages per call, claims each row atomically, retries failures with
exponential backoff, and gives up after five attempts. Without `RESEND_API_KEY` it returns 503 and
leaves messages queued. Without the secret it returns 401.

Schedule it from Vercel Cron (every five minutes is reasonable) or a Supabase scheduled function.
A cron entry is not included because the deployment host is not fixed in this repository.

## 4. Verification checklist

1. Apply migration `0021`.
2. Set the Supabase SMTP settings above and verify both sender domains in Resend.
3. Sign up with a real address. Confirm the verification email arrives, inspect SPF/DKIM/DMARC, and
   complete the link.
4. Request a password reset and complete it. Confirm the old password stops working.
5. Trigger an application decision and a ride status change. Query `notification_outbox`:
   - row exists with `status = queued` or `sent`;
   - recipient is the correct account;
   - payload contains no phone number, address or document.
6. Call the dispatcher with the secret and confirm `sent` plus a real delivery.
7. Confirm an invalid secret returns 401 and that the route is not reachable from the browser panel.
8. Record actual delivery evidence. Until then, describe email as configured by code, not live.
